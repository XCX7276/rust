| Правило | Что даёт |
| --- | --- |
| **Ядро без Bevy.** Мир, генерация, меш, физика, сохранение — в отдельном пакете `parodia_core`, который не знает про движок | всё важное проверяется тестами за секунды; при обновлении Bevy ядро не ломается |

## Что строим: видение и границы {#vision}

<p class="lead">Большой бесшовный воксельный мир, который генерируется по seed: горы, пещеры, биомы, вода, постройки и вписанные ориентиры. В нём — персонаж с прокачкой, оружием и магией из компонентов, мобы и данжи. Стиль — пиксель-арт в 3D, «красиво как Terraria».</p>

### Входит в проект

- Бесконечный по горизонтали мир, по вертикали −3072…+2048 блоков (20 столбиков по 256), без экранов загрузки. Расширение по высоте — смена двух констант.
- Генерация: рельеф, биомы с плавными переходами, пещеры по слоям глубины, руды, деревья, вода, постройки, ориентиры, данжи.
- Строительство: целые блоки, формы (ступеньки, скосы), мини-части (восьмушки, резьба ¼).
- Персонаж: коробка 0,6×1,8×0,6, своя физика по блокам, вид от 1-го/3-го лица.
- Сохранение: seed + только изменения игрока.
- Дальняя прорисовка (как Distant Horizons).
- Позже: мобы, бой, прокачка, магия, инвентарь и крафт.

### Не входит (сознательно)

| Не делаем | Почему |
| --- | --- |
| MMO на сотни игроков, секторы, Redis/NATS | не по силам одному; из старого ТЗ взяли только ядро |
| Фаза «сначала 2D» | мир сразу 3D |
| Сглаженный рельеф (marching cubes) | стиль — кубики с формами |
| Готовые ассеты из магазинов | могут быть недоступны; всё рисуем и генерируем сами |
| Тяжёлая графика (трассировка лучей, объёмные облака) | встроенная графика не потянет |

### Откуда взяты решения

Решения, которые уже приняты в Unity-проекте Parodia (размер блока, хитбокс, камера F5, формы блоков, сохранение изменений), **перенесены сюда без изменений** и отмечены в разделе 11. Unity-проект остаётся справочником: если не знаешь, как сделать этап, — посмотри, как он устроен там (`D:\Program\parodia\Parodia\Docs`).

## Методологии: как думаем {#method}

<p class="lead">Методология — это набор привычек, которые не дают проекту превратиться в «говнокод». Ниже — те, что реально нужны одному разработчику игры. Каждая объяснена одной фразой и примером.</p>

### 1. Функциональное ядро, императивная оболочка

Вся логика, которую можно описать как «на входе данные — на выходе данные», живёт в ядре и не знает про окно, кадры и Bevy. Bevy — тонкая «оболочка»: берёт результат ядра и показывает его.

- **Пример:** мешер принимает чанк и соседей, возвращает `Vec<u32>` упакованных вершин. Он ничего не знает про `Mesh`, `Handle`, `Commands`. Плагин рендера превращает этот массив в меш Bevy.
- **Почему:** такую функцию можно проверить тестом (`assert_eq!(faces, 6)`) без запуска игры. В Unity-проекте это было `Game.World.Data` — здесь то же, но компилятор сам запрещает ядру импортировать Bevy.

### 2. Данные отдельно от поведения (ECS)

Bevy построен на ECS (Entity Component System):

| Понятие | Что это | Пример |
| --- | --- | --- |
| **Entity** (сущность) | просто номер | игрок, моб, чанк на экране |
| **Component** (компонент) | данные, прикреплённые к сущности | `Transform`, `Health`, `ChunkPos` |
| **System** (система) | функция, которая обрабатывает все сущности с нужными компонентами | «всем, у кого есть `Velocity` и `Transform`, сдвинуть позицию» |
| **Resource** (ресурс) | одна общая вещь на всю игру | `VoxelWorld`, `GraphicsOptions` |
| **Message / Event** | сообщение «что-то случилось» | `BlockChanged`, `PlayerDied` |

- **Правило:** компонент — только данные (без методов с логикой игры). Логика — в системах.
- **Главное правило воксельной игры:** **блок — не сущность.** Блоки лежат в массиве чанка внутри ресурса `VoxelWorld`. Сущностью является только чанк **на экране** (его меш). 4 миллиарда сущностей-блоков убьют любую игру.

### 3. Одна точка изменения и события

Мир меняется только через `World::set_block`. Функция сама: помечает чанк «грязным» (нужно перестроить меш), запоминает изменение для сохранения, отправляет сообщение `BlockChanged`. Свет, вода, обрушение, звук подписываются на это сообщение — и никто не меняет блоки «в обход».

### 4. Данные вместо кода (data-driven)

Блоки, биомы, предметы, правила генерации — это **файлы данных** (`assets/data/*.ron`), а не `match` на 500 строк. Добавить новый блок = дописать запись в файл, без перекомпиляции логики.

```ron
// assets/data/blocks.ron
[
  (name: "stone", title: "Камень", solid: true, transparent: false,
   hardness: 1.5, textures: (all: "stone")),
  (name: "grass", title: "Трава", solid: true, transparent: false,
   hardness: 0.6, textures: (top: "grass_top", side: "grass_side", bottom: "dirt")),
]
```

### 5. YAGNI и вертикальный срез

YAGNI («You Aren't Gonna Need It» — «тебе это не понадобится»): не пишем код «на будущее». Вертикальный срез: каждый этап доводит **маленький кусок** игры до рабочего состояния через все слои (данные → логика → картинка → проверка), а не делает «весь рендер», потом «всю логику».

### 6. Детерминизм

Генерация зависит только от seed и координат. Никакого `rand::random()`, времени, порядка загрузки, `HashMap` с перебором в генерации. Проверяется тестом: «сгенерировать чанк дважды в разном порядке — хэш одинаковый».

### 7. Сначала замер, потом оптимизация

Не оптимизировать «на глаз». Сначала окно F3 / Tracy показывает, что тормозит, потом чиним именно это и снова меряем. Каждая оптимизация записывается в журнал с цифрами «было / стало» (в миллисекундах, не в FPS).

### 8. Решения записываются (ADR)

ADR (Architecture Decision Record — запись архитектурного решения): каждое важное решение — одна запись в `docs/DECISIONS.md`: «дата — решение — почему — какие были варианты». Через полгода ты не будешь помнить, почему чанк 32, а не 16, — а файл будет.

### Почему два пакета, а не один

| Если всё в одном пакете | Если ядро отдельно |
| --- | --- |
| можно случайно вызвать Bevy из генерации — и ядро привязано к движку навсегда | компилятор **не даст**: в `parodia_core/Cargo.toml` нет Bevy |
| тесты собирают весь Bevy (минуты) | `cargo test -p parodia_core` — секунды |
| обновление Bevy ломает всё | обновление Bevy трогает только `parodia_game` |

### Правила зависимостей

1. `parodia_core` не зависит ни от чего, кроме мелких библиотек (`serde`). **Bevy в нём запрещён.**
2. Внутри ядра — снизу вверх: `math → block → chunk → world → (gen, mesh, light, fluid, physics, lod, save)`. Нижние модули не импортируют верхние.
3. Плагины игры **не трогают внутренности друг друга**. Общаются через:
   - ресурсы ядра (`VoxelWorld` — все читают, меняют через `set_block`);
   - сообщения (`BlockChanged`, `ChunkMeshed`, `PlayerTeleported`);
   - публичные компоненты (`Player`, `ChunkPos`).
4. `main.rs` — только сборка приложения. Логики в нём нет.

### Путь одного действия: игрок ломает блок

| Шаг | Где | Что происходит |
| --- | --- | --- |
| 1 | `player/interaction.rs` | ЛКМ → луч DDA из `parodia_core::physics::raycast` → блок (x, y, z) |
| 2 | `player/interaction.rs` | `world.set_block(pos, AIR)` |
| 3 | `parodia_core::world` | чанк помечен «грязным», изменение записано в список для сохранения, в очередь — `BlockChanged` |
| 4 | `world/` | система переносит сообщения ядра в сообщения Bevy |
| 5 | `render/chunk_mesh.rs` | видит грязный чанк → задача в фоне: `parodia_core::mesh::build(chunk, соседи)` |
| 6 | `render/chunk_mesh.rs` | задача готова → массив вершин → `Mesh` Bevy → подменяет меш у сущности чанка |
| 7 | `light/`, `water/`, `save/` | реагируют на `BlockChanged` каждый по-своему |

### Порядок систем в кадре

Порядок задаётся группами (SystemSet) в `sets.rs`, а не «как получилось»:

<div class="formula">Input <span class="op">→</span> Player <span class="op">→</span> WorldEdit <span class="op">→</span> Simulation <span class="op">→</span> Streaming <span class="op">→</span> Meshing <span class="op">→</span> Camera <span class="op">→</span> Ui</div>

Физика тела, вода и мобы — в `FixedUpdate` (постоянный шаг, например 30 раз в секунду; по умолчанию у Bevy 64), картинка и интерфейс — в `Update`.

## Шаблон плагина {#plugin}

<p class="lead">Все плагины устроены одинаково. Открыл любую папку — сразу знаешь, где что лежит.</p>

```text
crates/parodia_game/src/player/
├── mod.rs            pub struct PlayerPlugin + регистрация всего ниже
├── components.rs     Player, Velocity, OnGround — только данные
├── resources.rs      PlayerSettings — общие настройки плагина
├── messages.rs       PlayerJumped, PlayerLanded — что плагин сообщает другим
├── movement.rs       системы движения (одна задача — один файл)
├── camera.rs         системы камеры
└── interaction.rs    ломать/ставить
```

```rust
// crates/parodia_game/src/player/mod.rs
use bevy::prelude::*;

mod camera;
mod components;
mod interaction;
mod movement;

pub use components::Player; // наружу — только то, что нужно другим

/// Игрок: ввод, движение коробки по блокам, камера, ломать/ставить.
pub struct PlayerPlugin;

impl Plugin for PlayerPlugin {
    fn build(&self, app: &mut App) {
        app.add_systems(Startup, movement::spawn_player)
            .add_systems(FixedUpdate, movement::move_player)
            .add_systems(Update, (camera::follow_player, interaction::break_and_place));
    }
}
```

```rust
// crates/parodia_game/src/main.rs — всё приложение на один экран
use bevy::prelude::*;

mod debug; mod player; mod render; mod settings; mod world;

fn main() {
    App::new()
        .add_plugins(DefaultPlugins)
        .add_plugins((
            settings::SettingsPlugin,
            world::WorldPlugin,
            render::RenderPlugin,
            player::PlayerPlugin,
            debug::DebugPlugin,
        ))
        .run();
}
```

<div class="callout" markdown="1">
**Про сообщения в Bevy 0.20.** В новых версиях Bevy буферные события называются **Message** (`add_message`, `MessageWriter`, `MessageReader`), а слово Event оставлено для «наблюдателей» (observers). Точные имена смотри в `cargo doc --open` → `bevy::ecs::message`. Если в примерах из интернета видишь `EventReader` — это старая версия.

## Правила кода {#code}

<p class="lead">Эти правила и есть защита от «говнокода». Нарушать можно, но осознанно и с комментарием «почему».</p>

### Имена (так принято во всём Rust)

| Что | Стиль | Пример |
| --- | --- | --- |
| Файлы, модули, функции, переменные | `snake_case` | `chunk_mesh.rs`, `fn build_mesh()` |
| Типы, трейты, плагины, перечисления | `CamelCase` | `VoxelWorld`, `PlayerPlugin`, `BlockId` |
| Константы | `SCREAMING_SNAKE_CASE` | `CHUNK_SIZE`, `PLAYER_HEIGHT` |
| Плагин | `<Что>Plugin` | `WaterPlugin` |
| Сообщение | что случилось, в прошедшем времени | `BlockChanged`, `ChunkLoaded` |
| Система | глагол + что | `move_player`, `spawn_chunk_meshes` |

Имена — английские (так принято в коде и так понятнее ошибки компилятора), **комментарии и документация — по-русски**.

### Размеры

| Что | Ориентир | Если больше |
| --- | --- | --- |
| Функция | до ~50 строк | разбить на шаги с понятными именами |
| Файл | до ~400 строк | разбить по задачам |
| Система | одна задача | две задачи — две системы |
| Параметры системы | до ~5–6 | вынести часть в `SystemParam` или разделить систему |
| Вложенность | до 3 уровней `if/for` | ранний `return`, `continue`, вынести функцию |

### Ошибки

- В ядре функции, которые могут не получиться, возвращают `Result<T, Ошибка>` или `Option<T>`.
- В игре — `warn!` / `error!` в лог и продолжаем работу. Игра не падает из-за битого файла настроек.
- `unwrap()` и `expect()` — только там, где ошибка = баг программиста, и с объяснением: `expect("реестр блоков загружен на старте")`.
- `panic!` в горячем цикле — никогда.

### Числа и константы

- «Магических чисел» нет: `16`, `0.55`, `1.8` — в константах ядра (`math::consts`) или в настройках (`assets/data/*.ron`).
- Единицы: **1.0 = 1 метр = 1 блок**. Время — в секундах (`f32`). Углы — в радианах внутри, в градусах в настройках.
- Оси (как в Bevy): **Y вверх**, правая система координат, «вперёд» камеры = −Z.

### Шейдеры и шум

- В буферах шейдера (storage, uniform) **нет `vec3`** — он выравнивается по 16 байт. Только `u32`, `f32`, `vec2`, `vec4` или `vec3` + поле-заполнитель.
- В шум — только координаты с масштабом (`x / масштаб`): в целых узлах шум Перлина равен 0.
- Общие функции шейдеров (свет, туман, облака) — в отдельных файлах и подключаются через `import` (WESL, без `#`), а не копируются.

### Производительность (всегда, а не «потом»)

- Блок — не сущность. Чанк на экране — сущность.
- В горячих циклах (меш, генерация) — без выделения памяти: буферы создаются один раз и переиспользуются.
- Тяжёлое (генерация, меш, свет больших областей) — в фоне (`AsyncComputeTaskPool`), главный поток только забирает готовое.
- Лимиты работ на кадр (сколько чанков сгенерировать, сколько мешей отправить).

### Документация в коде

```rust
/// Ставит блок и сообщает об изменении всем подписчикам.
/// Это единственный способ изменить мир (см. ТЗ, раздел 05, правило 3).
///
/// Возвращает `Err`, если чанк не загружен — незагруженное не трогаем.
pub fn set_block(&mut self, pos: IVec3, id: BlockId) -> Result<(), WorldError> {
```

`///` — описание для `cargo doc` (видно при наведении в VS Code). Комментарий пишет **почему**, а не **что**: «что» видно из кода.

### Тесты

| Что тестировать | Пример |
| --- | --- |
| Границы и отрицательные координаты | блок (−1, 0, −1) лежит в чанке (−1, 0, −1), индекс (15, 0, 15) |
| Записал — прочитал | `set_block` → `get_block` |
| Детерминизм | один seed, два порядка генерации → одинаковый хэш чанков |
| Сохранение | записать → прочитать → мир совпадает; старая версия формата читается |
| Меш | один блок в пустоте → 6 граней; два рядом → 10 |
| Физика | коробка не проходит в стену; автоподъём 0,55 работает, 1 блок — нет |

Маленькие тесты — внизу того же файла в `#[cfg(test)] mod tests`, большие — в `crates/parodia_core/tests/`.

### Антипаттерны: чего не делать

| Антипаттерн | Почему плохо | Как правильно |
| --- | --- | --- |
| «Бог-плагин» на 3000 строк | невозможно найти и поменять | плагин на фичу, файл на задачу |
| Каждый блок — Entity | миллионы сущностей, игра встаёт | блоки в массиве чанка |
| Логика мира в системах рендера | нельзя тестировать, ломается при обновлении Bevy | логика в ядре |
| Менять блоки напрямую в массиве чанка | свет, меш, сохранение не узнают | только `set_block` |
| `Query` на 8 компонентов с `&mut` всего | система делает всё; конфликты при параллельности | разделить систему |
| Строки как идентификаторы в горячем коде | медленно, опечатки | `BlockId(u16)`, строки только в файлах данных |
| Копипаста «как в соседнем файле» | исправишь баг в одном месте, в другом останется | общая функция в ядре |
| Закомментированный старый код | мусор, путает | удалить — он есть в git |
| «Сделаю универсально на будущее» | 80 % «будущего» не наступает | YAGNI, делать нужное этапу |

## Решения и открытые вопросы {#decisions}

### Приняты (перенесены из Parodia)

| Что | Значение |
| --- | --- |
| Масштаб | 1 единица = 1 м = 1 блок |
| Высота мира | было −3000…+2000; в ParodiaR округлено до −3072…+2048 (см. ниже) |
| Хитбокс игрока | коробка 0,6 × 1,8 × 0,6 м; автоподъём 0,55; прыжок 1,25; склон 45° |
| Камера | 1-е лицо по умолчанию, F5 — 3-е; колесо — прицельный зум, не дальность |
| Формы блоков | минимальный фиксированный набор: слои, ступеньки, скосы, углы; мини-части — восьмушки и резьба ¼ |
| Изменение мира | только `set_block` |
| Сохранение | seed + изменения игрока; подпись и номер версии формата |
| Мир | один бесшовный; данжи, шахты, деревни — структуры по seed прямо в мире |
| Сеть | сначала одиночная игра; ядро пишется так, чтобы позже был кооператив 2–8 с хостом |
| Стиль | пиксель-арт 16 пикс/м, контур 1 px, свет сверху-слева, ≤ 4 ступени на материал |
| Доступность | никакой информации только цветом (Н-07) |
| Обрушение | BFS только при разрушении, лимит за кадр, якорь — коренная порода |

### Новые для ParodiaR

| Что | Значение | Почему |
| --- | --- | --- |
| Движок | Bevy 0.20, Rust | полный контроль, без магазинов ассетов |
| Структура | workspace: `parodia_core` (без Bevy) + `parodia_game` | раздел 06 |
| Блок в памяти | `BlockId(u16)` + палитра в чанке | память и диск |
| Шаг симуляции | `FixedUpdate`, 30 раз в секунду | одинаково на любом FPS |
| **Чанк (вариант А)** | данные и меш — **секция 32³**; 8 секций друг над другом = **столбик 32 × 256 × 32** — единица подгрузки, сохранения и карты высот | выгоды высокого чанка (карта высот и биом на столбик, кэш 2D-шума ×256, меньше позиций для подгрузки) без минусов: правка блока перестраивает меш только одной секции 32³; бинарный меш на `u32` (как у Tantan) |
| **Высота мира** | −3072…+2048 = 20 столбиков = 160 секций; константы в `parodia_core::math::consts` | кратно 256 — границы мира совпадают со столбиками; память от высоты не зависит (в ОЗУ только чанки рядом) |
| Блоки в памяти на старте | массив + палитра в секции; RLE — позже для нетронутых и дальних столбиков | много правок мира (мини-части, вода) — массив проще и быстрее для случайного доступа |

### Открытые (решить до начала этапа)

| Вопрос | Варианты | Решить до |
| --- | --- | --- |
| Судьба Unity-проекта | продолжать параллельно / заморозить как справочник / ParodiaR только полигон | этап 0 |
| UI-библиотека | `bevy_ui` (встроен) или `bevy_egui` (удобнее для отладки, проверить версию под 0.20) | этап 1 |
| Плавающее начало координат | сразу (`big_space`) или когда дрожь станет заметна (~10–100 км) | этап 5 |
| Тени от солнца | нет / одна каскадная тень опцией | этап 10 |
| Модели персонажей | кубоиды с пиксельными текстурами / воксельные части / гибрид | этап 18 |

Каждый закрытый вопрос — запись в `docs/DECISIONS.md`.

## Словарь {#glossary}

| Слово | Значение |
| --- | --- |
| **Crate (пакет)** | единица сборки Rust: библиотека или программа со своим `Cargo.toml` |
| **Workspace** | несколько пакетов в одной папке с общим `Cargo.lock` и `target` |
| **ECS** | Entity–Component–System: данные (компоненты) отдельно, логика (системы) отдельно |
| **Plugin** | кусок приложения Bevy, который сам регистрирует свои системы и ресурсы |
| **SystemSet** | именованная группа систем, чтобы задать порядок «эти — после тех» |
| **FixedUpdate** | расписание Bevy с постоянным шагом времени (физика, симуляция) |
| **Message** | сообщение «что-то произошло», которое читают другие системы |
| **Чанк** | кусок мира N×N×N блоков: единица загрузки, меша и сохранения |
| **Меш** | набор треугольников, который рисует видеокарта |
| **Грязный чанк (dirty)** | чанк, в котором что-то поменялось и меш надо перестроить |
| **Детерминизм** | одни и те же входы — всегда один и тот же результат |
| **ADR** | запись архитектурного решения: что решили, почему, какие были варианты |
| **YAGNI** | «не понадобится»: не писать код на будущее |
| **DoD (Definition of Done)** | проверяемое условие «этап готов» |
| **LOD** | уровень детализации: вдали рисуем грубее |
| **SDF** | функция расстояния до формы — способ описать пещеры и хребты формулой |
